# Hermes 运维手册

> **Document type:** operations runbook
> **Audience:** operators, reviewers, incident responders
> **Depends on:** [`CONFIGURATION.md`](CONFIGURATION.md), [`SCHEDULER.md`](SCHEDULER.md), [`ARCHITECTURE.md`](ARCHITECTURE.md)
> **Reviewed:** 2026-11-17

## 1. 运维原则

- 线上服务按“先观察、再对账、后放行”的顺序运行。
- 任何连接异常、数据过期、账户状态不一致或未知订单都优先关闭提交闸门。
- 不在生产账户上做冒烟测试、重复启动或随意重试。
- 任务失败后先判断是否产生了部分副作用，再决定是否重跑。
- 变更前保存配置、日志、订单账本和当前状态；不要以删除文件代替回滚。

## 2. 启动前检查

### 2.1 主机和客户端

- Windows 计划任务的执行账户、解释器路径和工作目录正确。
- QMT/xtquant 客户端已按券商要求启动，`userdata_mini` 路径可访问。
- Python 依赖与 `requirements.txt` 版本兼容。
- `run.py` 的工作目录是 Hermes 根目录，否则相对配置路径可能解析失败。

### 2.2 配置

- 核对 `conf/config.ini` 的 `[client]`、`[strategy]`、`[logging]`。
- 核对 `[strategy] name`，不要只看策略目录。
- 核对 `conf/top10_v8_v1.ini` 的独立 `is_test`。
- 核对外部项目路径、解释器路径和评分/预测输出路径。
- 任何账户、策略、网关或风险配置变化都按变更流程执行。

### 2.3 数据

- `D:/tool/dataset/quant_data` 有最新可用行情文件。
- 策略所需的股票池、因子、评分、预测和状态文件存在且日期合理。
- Hephaestus-Forge 的预测或 Top10 产物覆盖当前输入日期。
- 不要为了补数据直接删除旧数据或重跑大规模任务；先查生产任务和数据契约。

## 3. 启动和放行状态

`run.py` 启动时先执行数据检查，再初始化账户。订单管理器创建时提交闸门关闭。只有在连接、订阅、查询、对账、账户校验和风险初始化均通过后，闸门才可能打开。

启动后必须确认：

1. QMT 连接成功。
2. 账户订阅成功。
3. 本地订单和券商订单完成对账。
4. 没有未知券商订单或缺失本地订单。
5. 资产和持仓校验通过。
6. 运行中的策略与配置中的活动列表一致。
7. Top10 若处于观察模式，未误改为真实下单模式。

任一项不满足时，保持观察/人工复核，不手动绕过闸门。

## 4. 日常监控

### 4.1 日志

主要日志：

```text
D:/tool/dataset/server_log/app.log
```

策略评分和部分策略运行产物：

```text
D:/tool/pycharm_workspace/Hermes/logs
```

关注：

- 启动前数据是否过期。
- 账户连接、订阅、对账和恢复状态。
- `submission_gate_reason` 或等价闸门关闭原因。
- 策略是否因非交易日、交易时段、状态文件或数据缺失跳过。
- 外部 Hep/Atropos 任务是否返回失败。
- 订单提交、拒单、撤单、成交回报和重复事件。

### 4.2 订单账本

订单账本默认位于：

```text
D:/tool/dataset/strategy_positions/orders_<account_key>.sqlite3
```

不要直接编辑 SQLite 账本。需要修复时保留副本、记录原因，并通过恢复/对账流程处理。

### 4.3 策略状态

策略持仓、成交记录和 Top10 状态位于共享策略数据目录。状态文件不是缓存，删除它可能导致重复调仓或持仓认知丢失。

## 5. 故障分级和处置

### P0：可能产生错误订单或账实不一致

例：未知券商订单、重复订单、持仓不一致、恢复对账失败、风险闸门异常打开。

1. 立即停止新的订单放行，保留进程和日志现场。
2. 不重启、不删除账本、不手工改状态文件。
3. 从券商端取得订单、成交、持仓和资产快照。
4. 对照本地 SQLite、服务日志和策略状态。
5. 需要人工决策时保持闸门关闭，记录处理人和时间。

### P1：服务不可用但账本一致

例：QMT 断线、订阅失败、外部数据过期、策略加载失败。

1. 查看 `QmtRecoverySupervisor` 和启动日志。
2. 判断是瞬时断线还是需要人工复核的持久错误。
3. 仅在确认没有未决副作用后按计划重启或重试。
4. 重启后重新完成账户对账，不沿用旧的“看起来正常”状态。

### P2：单策略或非关键数据异常

例：单个评分文件缺失、策略在非交易时段跳过、分析日志异常。

1. 保留故障文件和日志。
2. 确认其他策略和订单边界仍然正常。
3. 由策略负责人判断是否停用该策略或补产物。
4. 变更后更新数据契约或运行手册。

## 6. 变更、回滚和发布

### 变更前

- 说明影响的策略、账户、数据产物和订单路径。
- 保存当前配置哈希/副本和必要的运行日志。
- 在假网关、临时 SQLite 或观察模式中验证。
- 对结构性架构变化新增 ADR。

### 变更后

- 先验证配置解析和策略加载，不直接放行真实订单。
- 检查连接、订阅、对账、风险和闸门。
- 观察一个完整的策略周期或指定的验收窗口。
- 记录实际运行版本、数据日期和模型/评分版本。

### 回滚

- 优先恢复已验证的代码/配置版本，不删除生产产物。
- 涉及订单状态时先关闭闸门，再保存现场，再执行回滚。
- 回滚后重新连接、订阅和对账；不要假设重启会自动修复账本。

## 7. 停止和重启

停止或重启线上服务前，应确认：

- 当前没有正在提交或等待回报的关键订单操作。
- 已保存服务日志和订单/成交现场。
- 已知重启会触发账户初始化和重新对账。
- 计划任务不会与手工启动形成两个 Hermes 实例。

不要通过删除进程生成的日志、SQLite 或状态文件来“清理后重启”。
